### Sub-shape adoption count vs per-cycle decision count — methodological distinction

Cycle 92's B sharpening surfaced a previously-conflated distinction: **sub-shape adoption count is the M2 cost-inheritance metric (per audit#454 absorption)**, but it is the upper-bound on per-cycle decision count, not the actual rate. Most adopted sub-shapes fire bursty or situationally:

- **Memory consolidation** (cluster H sub-shape 2) — fires when threshold-score reaches gating value, possibly every 5-10 cycles.
- **Branch-spawning** (cluster C sub-shape 3) — fires when planner observes branching-merit signal, possibly every 5-20 cycles.
- **What-if reasoning** (cluster B sub-shape 7 + cluster C sub-shape 3) — fires when ambiguity is high enough, possibly every 10+ cycles.
- **Plan-lifecycle promotion** (cluster F Axis 5) — fires at plan-completion time, possibly every 3-10 cycles per active plan.

The P3 PARTIAL-FLAG language in B's first iteration ("3-4× v1") was about sub-shape adoption count (43:6 = 7×) but **per-cycle decision count is closer to 1×** when sub-shape firing rate is accounted for. This is a methodological refinement to P3 evaluation: distinguish *adoption count* (system has the mechanism) from *firing rate* (mechanism fires per cycle) when grading self-management cost.

This refinement applies to all 3 candidates' P3 grades:

- **C's PASS-WITH-NOTE:** 24 sub-shapes adopted (3 more than A); firing rate accounting weakens the "3 more" — replay fires at plan-replay time (rare); event-trigger fires per inbound event (varies); plan-lifecycle state-machine fires at promotion time (medium-rare). - **B's PARTIAL-FLAG:** 43 sub-shapes adopted; firing rate accounting weakens "3-4× v1" substantially (per cycle 92 sharpening: aggregate ~80-110% v1 decision count, not 3-4×).

Cycle 92 sharpening surfaces this refinement; future P3 evaluation should distinguish adoption count from firing rate.
